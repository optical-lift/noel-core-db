## Why the green combined clone is NOT the migration

The held `candidates/atlas/20261028235811_atlas_care_single_done_signed_proof_v1.sql` is ~269 KB and begins with `BEGIN;` and an explicit `CLONE TEST ONLY` guard requiring named synthetic Auth and growing-object rows. It assembles **3 CREATE TABLE declarations, 34 CREATE/REPLACE FUNCTION declarations (including replacements of native guards), 16 CREATE TRIGGER declarations and 1 CREATE VIEW** plus test-recovery and parity source. These are deliberately composed for **ephemeral source-acceptance verification**, not a scoped deployment or proof of independent release custody. Its literal production execution must remain refused. The `01_assigned_activity_recognition_held.sql` P1 fragment (~12 KB) is distinct, but is deliberately **not** `BEGIN/COMMIT` wrapped, not a canonical migration, and calls absent live C1 physical Result writer.

The source-only `03_local_rollback_source_check.sh` wraps `01+02` in **BEGIN/ROLLBACK on a disposable clone**. That is an acceptance tool, **not** a production rollback plan. No general automatic rollback of an append-only link, accepted Result or Done has been established. For prospective release, design a separately reviewed stop-new-writes / preserve-existing-evidence / governed forward-remediation method, with migration failure atomicity; do not delete immutable physical evidence to roll back a release.

The held R02 care writer has a campaign-successor path. The P1 source refuses `sourceStandingCampaignId` / `owner_standing_successor_v1` originals; keep that fail-closed guard. **P3 cutover is a prerequisite for expanding P1 to campaign-related Work**, not authority to silently create successor Work from a Result. P2 retrospective governor adjudication, P4 Atlas one-sentence presentation, P5 Household/Event remain independent and HELD.

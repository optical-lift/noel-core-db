# P1C — independently approved derived financial revision (held contract)

Status: source design, not accepted or released. Depends on G3, P0, P1A and P1B. Noel owns canonical custody and SQL; Us owns only the restricted signed transport. The existing owner-only `carry_adopt_derived_revision_v3` is revoked under P0 and cannot be exposed as the approval endpoint.

## One bounded result

An owner of one G3-approved original financial Case can propose one derived revision from an exact source event cutoff. The source computes the candidate using `carry_candidate_core_v3`, records the baseline revision ID, line count, projection version, cutoff, canonical candidate digest and an envelope digest in an immutable proposal. No revision or seal event is created at proposal time. The owner grants one or more distinct, currently canonical Persons permission to review only this exact proposal for 5 minutes to 7 days, with individual revocation. A reviewer receives the exact derived lines and source causes needed to judge this proposal, not full Case history, other Cases or a roster. P2 governs full Case disclosure separately.

A signed, currently authorized reviewer approves one proposal with an independent decision key and exact envelope digest. The database locks that proposal and its stream, rechecks both live canonical Person bindings, unexpired and unrevoked grant, G3 opening provenance, the original adopted baseline, the current last event sequence and the fresh database-derived candidate digest. In one database transaction it creates one derived revision and its exact lines, appends one v1 `REVISION_SEALED` event, and writes an immutable approval decision tying both canonical Persons, exact proposal/grant, revision, event, digest and cutoff. It accepts no caller-provided amounts, rows, source digest or owner identity as authority. A retry of the same signed decision returns the original IDs without writing; a different actor, key, envelope or cutoff fails closed. Concurrent reviewers or a revocation race yield at most one effective decision. An expired grant cannot approve even if its proposal was formerly visible.

P1C must replace the old owner-only adoption function with a private internal implementation that is callable only inside the independently approved source transaction. Merely wrapping a still-granted owner-only function does not close P0. The restricted `us_carry_backend` role gets narrowly scoped EXECUTE on proposal, grant/revoke, packet and independent approve functions, no direct table INSERT, line write, v1 append or older adoption EXECUTE. `anon`, `authenticated` and `service_role` receive no new access. This held change is not generated as a production migration.

## RiverSong one-run acceptance gate

Pin exact Us and Noel candidate SHAs; reject an unexpected branch, ref or source digest. On the dedicated Us RiverSong runner, use job-local loopback PostgreSQL and genuine GoTrue with at least owner, reviewer and outsider canonical Persons. Apply the original financial baseline, held Carry v1/v2/v3 and G1/G2/G3/P0/P1A/P1B/P1C in dependency order to a disposable database. Run source privilege assertions and signed HTTP tests through the separate internal service and restricted role. Assert owner proposal creates no seal, reviewer sees only granted proposal, outsider and owner self-approval fail, revoked/expired/stale grant fails, stale baseline/cutoff or altered digest fails, two independent concurrent reviewers create exactly one revision/seal/decision, exact retry returns the same IDs, original adopted baseline remains unchanged, and older owner-only/service-role writers remain denied. Clean all temporary identities, credentials, processes and database on success or failure. Report exact source SHAs and run URL in the existing Noel acceptance file and Us `RIVERSONG_LOCAL_STAGING_STATUS.md`.

Do not mark P1C complete from synthetic Python tests or the automatic workflow's older pinned PostgreSQL fixture. Do not ingest real finances, merge drafts, deploy hosted SQL or change Atlas. P2–P8 and 10D remain open.

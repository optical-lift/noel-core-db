# Atlas Development Proof — Elm Flower Preparation / Bunching v1

**Status:** Architecture proof; no executable Development schema authorized  
**Date:** 2026-09-22  
**Domain:** Elm Farm production operations  
**Existing live source authority:** Company Operating Knowledge + Flower Preparation runtime  
**Purpose:** Test Development against a domain structurally different from Camps International activity/curriculum development.

## 1. Proof question

Can the same four Development contracts represent the process of turning partial production knowledge into a reproducible/delegable operating procedure without turning Development into a camp-specific content system?

## 2. Existing live Elm truth

Production architecture already contains established Elm Company Operating Knowledge for bunch size.

The established rules include:

```text
Default cut flowers:
10 stems per bunch unless a more-specific established product rule applies.

Goldenrod:
5 stems per bunch.

Sunflowers:
5 stems per bunch.
```

These are scoped, versioned, established institutional rules.

The Flower Preparation v2 runtime can apply an established Operating Knowledge default when the Owner does not explicitly supply a stems-per-unit value, while preserving provenance and keeping explicit Owner direction authoritative.

Therefore Elm already proves several things Development should consume rather than duplicate:

- reusable standard;
- specificity;
- exception;
- runtime resolution;
- exact provenance;
- explicit human override boundary;
- immutable later accounting.

## 3. What the live rule does not establish

The live bunch-size knowledge should not be interpreted as a complete delegable flower-preparation procedure.

The cited source establishes quantity-per-bunch semantics.

It does not, by itself, establish every possible procedure criterion such as:

- handling sequence;
- stem quality acceptance;
- tool requirements;
- hydration/holding steps;
- product-specific preparation beyond bunch count;
- timing limits;
- acceptable substitution;
- complete worker qualification;
- complete safety expectations;
- complete evidence of finished quality.

Some of those may already exist elsewhere in Atlas or operational practice.

This proof does not claim they are absent from reality.

It claims only that the bunch-size source is insufficient to infer them.

That is exactly the epistemic distinction Development must preserve.

## 4. Candidate Elm Procedure Development Standard v1

This is a proof model, not established Elm policy.

Candidate criteria could include:

### Output definition

- exact requested product/output;
- bunch/unit quantity;
- product-specific exceptions;
- substitution policy.

### Preparation method

- sequence;
- handling instructions;
- tools;
- location/environment;
- expected duration where material.

### Quality

- acceptable stem condition;
- completion semantics;
- rejection/rework conditions;
- inspection evidence.

### Responsibility

- which role/person may prepare;
- when owner/manager direction is required;
- what can be defaulted from Operating Knowledge.

### Execution

- runtime resolution is deterministic;
- provenance is retained;
- worker can act without reconstructing owner knowledge from memory.

### Revision

- how later product-specific standards supersede defaults.

## 7. How Development reduces owner labor

Without Development, an owner may repeatedly answer:

> How many stems go in this bunch?

Current Operating Knowledge already eliminates that repetition.

Development extends the same logic to the questions that remain.

Suppose five product procedures are all missing the same “acceptable stem condition” decision.

Development should be able to discover that this may be a family-level standard.

Instead of resolving it five times:

```text
candidate shared rule
-> evidence / owner judgment
-> established Operating Knowledge
-> five Cases reconsider
-> inherited Criterion resolution where applicable
```

That is the same labor-reduction law required by CI.

## 8. Work delegation proof

A missing procedure decision can create Company Work without giving the worker policy authority.

Examples:

```text
Criterion:
actual average bunch-preparation time unknown

Work:
time 20 representative bunches
-> Result / Evidence
-> Criterion reconsideration
```

```text
Criterion:
quality failure pattern unknown

Work:
record rejected/reworked bunch reasons for two weeks
-> Evidence
-> owner/practitioner review
```

The worker collects evidence.

The institution decides what standard to establish.

## 9. Human authority proof

Suppose evidence shows two plausible quality thresholds.

Development Reconciliation may classify:

```text
authority_required
```

A Decision Requirement should reach the exact current authorized actor.

The human decision then establishes or versions the owning-domain standard.

Development records the Criterion Resolution basis.

It does not become a generic approval authority.

## 10. Continuation proof

If a new product-specific bunch rule is established:

```text
Operating Knowledge v2 established
-> Development continuation
-> affected criterion(s) reconsider
-> procedure gate(s) recompute
```

A more-specific product rule may resolve one criterion without completing the entire procedure.

Again, the same continuation law as CI applies.

## 11. Release proof

## 12. Structural differences from CI

This proof is useful because Elm is not merely another training/activity domain.

CI Washers involves:

- physical game design;
- construction;
- portability;
- children/counselors;
- instructional script;
- spiritual/relationship use;
- human qualification.

Elm bunch preparation involves:

- production output;
- default/exception operating rules;
- owner direction;
- worker execution;
- quality/completion;
- runtime rule resolution.

Despite those differences, the same Development mechanics survive:

```text
Standard Version
-> Case
-> criterion-by-criterion accounted state
-> evidence / Work / authority handling
-> inherited reusable knowledge
-> continuation/gate recomputation
-> released target-domain version
```

## 13. Result

The Elm proof does not require any CI-specific noun in the universal Development contracts.

It also proves that Development should consume Company Operating Knowledge rather than replace it.

The architecture comparison therefore supports the four Development contracts as a plausible Atlas-wide domain shape.

It still does not by itself authorize a production schema. The next step is a field-by-field cross-domain qualification audit and, if it passes, the smallest executable candidate.

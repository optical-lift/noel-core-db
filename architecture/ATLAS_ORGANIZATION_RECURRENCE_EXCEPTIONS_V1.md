# Atlas Organization Recurrence + Exception Kernel v1

## Purpose

Atlas must distinguish among:

- a canonical **occurrence** that actually exists,
- an Organization-owned **recurrence rule** describing when something is expected to repeat,
- an **exception** to one nominal recurrence instance, and
- the resulting Organization-private **recurrence instance expectation**.

A recurrence rule is not itself an occurrence. Generating a date from a rule must not silently manufacture canonical Shared Intelligence event identity.

## Core model

```text
Organization recurrence rule
        ↓
nominal recurrence dates
        ↓
Organization exception layer
        ↓
expected recurrence instances
        ↓
optional canonical occurrence binding
```

This gives Atlas an explicit distinction between:

```text
"this normally happens"
"this date is an exception"
"this specific real event exists"
```

## Tables

### `atlas.organization_recurrence_rules`

Organization-private schedule law.

v1 supports:

- `weekly`
- `monthly_nth_weekday`

The rule owns:

- effective date range
- timezone
- weekday(s)
- monthly ordinal(s), when applicable
- local start/end time
- interval
- Organization-private payload/metadata

Rules are Organization-scoped and reusable across domains. A rule is not Elm-specific and is not limited to community events.

### `atlas.organization_recurrence_exceptions`

One exception to one nominal date generated by a recurrence rule.

v1 actions:

- `skip`
- `override`
- `move`

An exception may reference an `organization_temporal_binding`, allowing canonical date meaning such as Thanksgiving to explain why a recurrence changes.

Examples:

```text
rule: 4th Thursday evening
nominal date: 2026-11-26
exception: skip
temporal binding: Thanksgiving 2026
reason: No Thursday at Elm
```

or:

```text
rule: first Monday
nominal date: 2026-09-07
exception: move
replacement date: 2026-09-08
```

### `atlas.organization_recurrence_instances`

The resolved Organization-private schedule expectation.

Each row preserves:

- `source_local_date` — the nominal date produced by the rule
- `local_date` — the effective date after an exception
- expected start/end timestamps
- `schedule_state` — `expected`, `skipped`, `overridden`, or `moved`
- optional exception
- optional canonical `occurrence_binding_id`
- `realization_state` — whether a real occurrence has been attached

The recurrence instance is not canonical event truth. It is Organization schedule expectation.

## Materialization rule

Refreshing a recurrence rule produces or updates recurrence-instance expectations only.

It **does not create `local_intel.occurrences`**.

If a real event exists, Atlas may attach the Organization's existing canonical occurrence binding to the expected recurrence instance.

This prevents:

```text
schedule rule → accidental fake event identity
```

and preserves:

```text
schedule expectation → explicit reality resolution → canonical occurrence
```

## Exceptions and temporal markers

Temporal markers and recurrence exceptions are complementary.

A temporal marker says:

> This date carries meaning.

An exception says:

> This Organization's recurrence behaves differently on this nominal instance.

Therefore Thanksgiving can exist once as canonical temporal reality while many Organizations independently decide whether it:

- closes programming,
- moves a recurring meeting,
- changes hours,
- has no effect,
- or causes another Organization-specific schedule behavior.

## Initial Elm implementation

The old `community_programs.cadence` JSON for Thursdays at Elm is retained as compatibility/history, but recurrence authority moves to two generic Organization recurrence rules:

1. `thursdays_community_mornings`
   - Thursday
   - first and third Thursday of the month
   - 9:30–11:30 a.m.
2. `thursdays_seasonal_evenings`
   - Thursday
   - second and fourth Thursday of the month
   - 6:30–8:30 p.m.

The Nov. 26, 2026 fourth-Thursday evening gets a `skip` exception linked to Elm's Thanksgiving temporal binding.

Existing canonical occurrences are attached to the resulting recurrence instances. No duplicate events are created.

## Governing rule

```text
recurrence describes expected schedule
exception modifies one nominal schedule instance
occurrence records real event identity
temporal marker records date meaning
```

These four concepts must remain distinct even when a calendar renders them together.

# Atlas Implementation Reality Organization Unit Promotion v1

## Purpose

This tranche graduates the first structural Reality Sentence family after Institutional Person:

`Organization has Organization Unit`

It extends Reality Candidate grammar and adds a read-only promotion preview plus canonical rerender for Organization Unit truth. It does not add the mutation command in this preview tranche.

The owning canonical object already exists as `atlas.organization_units`. Organization Unit is a durable institutional operating body inside an Organization. It is not a Principal portfolio lens, employee assignment, farm-specific object, or implementation-case artifact.

## Canonical truth owner

`atlas.organization_units` owns Organization Unit identity and current structural fields:

- `organization_id` — institutional custody root;
- `parent_unit_id` — optional parent Organization Unit in the same Organization;
- `name` — human institutional name;
- `unit_kind` — open organization-defined classification;
- `stable_key` — owning-domain internal key;
- `status` — active / inactive / archived.

Reality Candidate custody never becomes a second Organization Unit store.

## Reality Sentence grammar

Operation:

`organization_unit.establish`

Bindings:

- subject = proposed `organization_unit`;
- object = canonical `organization`;
- context = optional canonical `organization_unit` parent.

Semantic payload:

- required `unitKind` = nonblank string.

The parent is an identity participant and therefore belongs in a binding. It must not be hidden inside `semantic_payload`.

The internal `stable_key` is not human-authored semantic meaning. It is generated by the owning Organization Structure domain when establishment executes.

## Human rendering

Root unit:

`Organization has Organization Unit Unit Name (unitKind).`

Nested unit:

`Organization has Organization Unit Unit Name (unitKind) inside Parent Unit.`

The canonical rerender is derived from canonical Organization Unit truth, never copied from the candidate's literal wording.

## Authority

The practitioner is a carrier of implementation work, not the source of Organization structural authority.

Readiness requires:

1. an open Implementation Case;
2. the signed-in assigned practitioner;
3. an active root Ledger entitlement binding for the candidate Organization;
4. active Organization participation in that Ledger;
5. a verified setup sponsor whose canonical Principal has governing authority over that Ledger;
6. a proposed Organization Unit subject;
7. canonical Organization binding;
8. canonical same-Organization parent binding when a parent exists;
9. a nonblank `unitKind`.

Initial Scope does not establish Organization Unit truth. Finding adjudication may supply provenance/evidence, but does not execute this family.

## Identity / duplicate rule

A proposed unit whose human name already resolves to an active canonical Organization Unit in the same Organization is not silently duplicated. Preview returns the existing canonical identity and requires the candidate to be reconciled to that identity instead of treating a second row as harmless.

Different human labels may normalize to the same internal stable-key base. That is an implementation-key collision, not identity proof. The later owning-domain command must generate a collision-safe internal key without asking the practitioner to author one.

## Preview boundary

This tranche is read-only.

It may:

- validate grammar, semantic payload, scope, sponsor authority, parent custody, and duplicate identity;
- render an already-promoted Organization Unit from canonical truth;
- report whether the exact future mutation RPC exists and is executable.

It may not:

- insert/update/delete Organization Units;
- mutate Reality Candidate state;
- create a parent relationship;
- create a Position;
- infer `unitKind`;
- establish Initial Scope;
- use a generic Reality executor.

## Mutation tranche that follows

After this preview is production-live, the separate owning-domain command tranche will add:

`public.promote_implementation_reality_organization_unit_self_api_v1(uuid)`

That command must:

1. re-run the released preview;
2. generate the internal stable key in Organization Structure;
3. establish exactly one Organization Unit or return a canonical conflict;
4. return an establishment receipt;
5. mark only that Reality Candidate promoted with the canonical Organization Unit reference;
6. canonical-rerender through `render_organization_unit_reality_consequence_v1`.

## Next structural dependency

After Organization Unit is promoted, Position grammar must be corrected so a Position binds to a canonical Organization Unit rather than directly to the Organization alone.

Sequence remains:

`Organization Unit → Position → Responsibility → Position↔Responsibility → Person↔Position appointment`

Each family graduates independently.

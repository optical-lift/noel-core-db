# Atlas Implementation Reality Candidate Semantic Payload v2

## Purpose

Reality Candidate v1 can identify the semantic participants in a proposed statement and preserve evidence, establishment basis, and provenance. That was sufficient for the first executable promotion family:

canonical Person + canonical Organization → Institutional Person Record

The remaining structural families need additional canonical meaning that is not an identity:

- Organization Unit: unit kind and optional parent-unit relationship;
- Position: Organization Unit plus position kind;
- Responsibility: responsibility kind;
- Position Appointment: appointment kind and effective-time window.

Those values must not be smuggled into provenance, evidence, or establishment authority.

This tranche adds one neutral custody concept: semantic_payload = operation-specific qualifiers that are part of what the proposed reality means.

It deliberately does not add any new establishment operation.

## Governing separation

- subject / object / context bindings = which things participate
- semantic_payload = additional operation-specific meaning
- evidence_refs = what supports the proposal
- establishment_basis = why canonical establishment would be lawful
- provenance = how and where the proposal entered custody
- canonical consequence = truth established later by the owning domain

None of these categories substitutes for another.

## Compatibility law

Reality Candidate v1 remains unchanged. The table gains semantic_payload jsonb NOT NULL DEFAULT '{}'. Existing v1 rows therefore receive an empty payload without changing their contract identity or current browser API.

New additive membranes are public.create_implementation_reality_candidate_self_api_v2(...) and public.implementation_reality_candidates_self_api_v2(case_id). The current Workbench can continue using v1 until private Atlas CI/deployment is available.

## Promotion immutability

Before promotion, a candidate may still be corrected. After promotion, semantic_payload becomes immutable provenance. A later correction to established reality must use the owning domain's normal correction/supersession path; it must not rewrite what the promoted candidate originally meant.

## Owning-domain law

Common custody does not validate the business meaning of every payload key. Each promotion family owns its own required semantic contract. For example, appointment may require appointmentKind and beginsAt; Organization Unit may require unitKind.

The common v2 membrane proves only that the payload is a JSON object. It does not infer defaults, choose meanings, or establish truth.

## Technical identifiers

Human semantic payload must not become a dumping ground for implementation identifiers. Durable internal keys such as stable_key belong to the owning domain and may be generated by that domain. A practitioner should not have to type an internal database identity into a Reality Sentence.

## Non-goals

This tranche does not:

- add organization_unit.establish;
- change the existing operation whitelist;
- change existing operation shapes;
- establish an Organization Unit, Position, Responsibility, or Appointment;
- alter the production-live Institutional Person promotion;
- alter Initial Scope authority;
- change Person Position, Domain Exposure, Notebook reconciliation, Index, Today, or action authority;
- grant AI any canonical mutation authority.

## Next dependency

Once semantic payload v2 is live, the structural promotion sequence can proceed without invented facts:

Organization Unit grammar + promotion → Position grammar corrected to bind canonical Organization Unit → Position promotion → Responsibility promotion → Position↔Responsibility definition → Person↔Position appointment.

Each family still graduates independently through candidate → read-only preview → owning-domain command → canonical receipt → canonical rerender.

# Atlas Organization Ledger — promotion plan

## Current state

As of September 5, 2026:

- Product Map `PMD-018` has selected Organization Ledger as the primary active Organization encounter.
- `OPS-01` is deeply mapped.
- Generic Organization Ledger DDL/read/projection behavior has passed a live-schema rollback proof.
- Production → Company Work direct materialization has passed a live-schema rollback proof.
- No production Ledger schema has been created.
- No Production writer has been changed.
- No legacy Journal reader/writer has been removed.
- No UI runtime has been pointed at unreleased authority.

## Why promotion is deliberately staged

The legacy farm Journal is already live and valuable, but it is not the generic Ledger contract. A direct in-place rename/generalization would combine three unsafe changes:

1. canonical/read-model semantics;
2. authorization scope;
3. product behavior.

The selected path uses Succession + Continuity:

`legacy farm Journal continues`
+ `new Organization Ledger projection becomes live beside it`
→ `meaningful legacy events adapted into new projection`
→ `new domain adapters publish directly`
→ `readers migrate`
→ `legacy Journal retired only when continuity is proven`.

## Promotion 1 — release generic projection storage + read contract

Generate the migration through the repository's normal Supabase migration workflow.

Materialize the already-proved contract from `atlas-organization-ledger-v1.sql` with production names:

- `atlas.organization_ledger_entries`
- `atlas.organization_ledger_subjects`
- monotonic projection revision sequence/cursor
- internal service-only projection admission function
- internal typed-subject link function
- conservative organization-owner read API
- RLS enabled
- direct authenticated table access revoked

### Required migration review before application

- migration timestamp generated by Supabase CLI/workflow, not hand-authored;
- exact FK/index names checked against current main;
- SECURITY DEFINER functions reviewed for fixed search path and explicit auth boundary;
- PUBLIC/anon/authenticated execute grants reviewed;
- sequence privileges reviewed;
- current Supabase security/performance advisors run after application in development/preview;
- rollback/rebuild strategy documented.

### Do not add yet

- Realtime publication merely because the table exists;
- public universal manager access;
- a generic semantic-event canonical writer;
- automatic client-side mutation;
- Stripe payment semantics;
- farm-specific event enum.

## Promotion 2 — legacy Journal adapter

Add an internal idempotent adapter that can project qualifying `journal_event_index` rows into Organization Ledger.

Rules:

- preserve `journal_event_index.id` / event key as provenance/correlation;
- preserve `occurred_at`;
- set `source_domain='legacy_journal'` or a more precise source-domain mapping only when actually warranted;
- copy generic `journal_event_subjects` into Ledger subjects where legitimate;
- translate visibility through explicit new authorization policy rather than copying `farm_shared`/`management` as universal roles;
- do not infer purpose/designation from title text;
- use `unresolved` where the legacy projection does not provide enough governed linkage;
- exact replay must not duplicate Ledger history.

Backfill can then be run incrementally and compared against the legacy Journal without switching the UI.

## Promotion 3 — Production direct Company Work

Promote the verified source convergence:

`production_bed_assignment`
→ direct Work Requirement
→ direct Work Item
→ Work time contract.

Refactor/succeed `reconcile_production_capacity_work_v1()` so the source path is:

1. validate Production state/destination/capacity;
2. establish Company Work directly and idempotently;
3. **do not resolve `worker_key='anna'` inside Production**;
4. if an authorized Responsibility allocator already knows the responsible human, allocate separately;
5. otherwise leave Work open/unassigned and expose unresolved responsibility;
6. create a legacy Task/planned occurrence only as an optional execution adapter while old Worker Day needs it.

The source-derived Work stable key must not change when assignee, day placement, or execution carrier changes.

## Promotion 4 — first Ledger consequence adapters

Attach projection admission to meaningful source consequences, not row triggers in bulk.

Minimum first chronology:

- Production lot readiness established;
- destination/preparation requirement established;
- Company Work established;
- Responsibility allocated/released where governed;
- worker completion/result established;
- Company Work requirement satisfied;
- Production prerequisite/gate reconciled.

Each adapter must provide:

- durable event key;
- source domain + semantic type;
- occurrence time;
- source subject links;
- truth status;
- designation status;
- provenance/correlation.

The Ledger projector must never become the writer that establishes Production or Work truth.

## Promotion 5 — Worker result closure

Current Worker Day/pilot surfaces are downstream delivery mechanisms. Before retiring legacy Task carriers:

1. define the governed Company Work result command;
2. preserve worker result/evidence separately from source-domain conclusion;
3. close/satisfy Work only under the Work result contract;
4. call/re-evaluate Production source consequence;
5. prove the source can reject/retain unresolved state even if the worker tapped Done;
6. project both Work and Production consequences to Ledger;
7. preserve Work Accountability visibility without leaking private Completion Support cause.

## Promotion 6 — Harvest / Commerce adapters

Existing Flower Commerce can be projected before being generalized because its source-domain lifecycle is already explicit.

Attach meaningful Ledger movements for:

- Harvest result;
- Ready inventory establishment/change;
- Demand created/committed/cancelled;
- allocation/release/coverage consequence;
- Sale established/cancelled;
- fulfillment custody/result;
- buyer-history consequence where governed.

Availability remains a derived Commerce/Inventory position:

`Ready supply − active allocation/custody − other unavailability`.

Do not write availability as independent canonical truth merely to populate the Ledger/UI.

## Promotion 7 — fulfillment work convergence

Where Flower fulfillment still creates/depends on a legacy Task, converge it onto the same shared Company Work grammar:

`Sale/fulfillment requirement`
→ Company Work
→ Responsibility
→ optional legacy execution adapter
→ fulfillment result.

Katie is a legitimate Responsibility target only through governed institutional identity/Responsibility, not because Commerce knows a hard-coded worker key.

## Promotion 8 — Stripe/provider evidence

Map and implement only the Integration/Reality side first:

`Stripe provider event`
→ Connected Source / Provider Operation
→ Source Observation
→ Evidence
→ Organization Ledger line with `truth_status='observed'`
→ designation `unresolved` until matched.

The Ledger may say:

> Stripe reported $35 received — economic reconciliation pending.

It may not say `Sale paid` merely because the provider event exists.

## Promotion 9 — common Money Collection authority

Before Stripe can close economic state, release the common reusable Money contract:

- obligation basis from Sale/source-owned receivable;
- provider/manual payment observations;
- allocation/matching of receipt evidence to obligation;
- partial payments;
- reversal/refund/chargeback handling;
- multi-obligation ambiguity/conflict;
- derived paid/open balance;
- provenance and reconciliation history.

Only the Money authority may establish the canonical economic consequence consumed by Ledger.

## Promotion 10 — persistent Organization runtime + OPS-01

Only after the backend read contract is live:

- load Organization orientation once;
- load current Ledger window with revision/cursor;
- maintain it incrementally;
- open source-domain details without reconstructing the institution;
- keep private Person/Household data out of institutional projections;
- use lenses (People, Production, Inventory, Sales, Money, Integrations) over the same governed institution rather than disconnected apps.

## Release gates

Do not release Organization Ledger UI if any are true:

- farm-specific Journal remains the only source;
- direct client writes can mutate Ledger rows;
- owner/manager authorization is inferred from UI role labels;
- replay duplicates events;
- unresolved state is suppressed;
- ledger chronology can leak private Personal Atlas facts;
- Production still creates work by finding Anna directly;
- Worker Day completion can manufacture Production truth;
- Stripe observation can manufacture `paid` state;
- the reference-company pressure test requires farm-only fields.

## Immediate next executable step

Generate the actual Organization Ledger migration from the already-passing rollback proof using the repository's normal Supabase migration generator, review it, apply it to a safe development/preview target, run advisors/tests, and only then begin the legacy Journal + Production adapters.

Do not invent the migration prefix by hand if the generator is unavailable.
